# 采购公告采集与更正追溯平台（ProcureWatch）

面向采购团队的多来源招标公告采集、更正识别与采用依据追溯平台。采购专员可以从任意一项**报名截止时间**追溯到它来自哪份公告、哪个正文版本、哪条更正，以及还有哪些内容尚未核实。

技术栈：**Go 1.26 + Gin + Vue 3（Vite/Pinia/Vue Router）+ PostgreSQL 18**，另含一个 Go 实现的**多来源样本站点**（页码分页 / 游标分页 / 详情原址修订）。

---

## 1. 它解决了什么问题

| 现实情况 | 平台的处理纪律 |
| --- | --- |
| 同一项目先发总公告，再按标包补设备清单 | 项目与标包分别建模、分别计数；同项目编号自动归并，补充清单作为新文档/新字段保留 |
| 日期更正有时直接替换原网页，有时另发通知 | 另发通知走“更正”流程；原址换文由定期复查对比**正文指纹**发现，两种都留存全部历史版本 |
| 旧链接消失 ≠ 撤标 | 链接失效只记为 `不可访问`，**项目状态不变**；只有明确撤标公告才置为“已撤标” |
| 标题相近的两个采购不一定同项目 | 只凭**显式采购编号**自动关联；编号缺失/冲突转“关联候选”交人工确认 |
| 只抓新链接会漏原址修改；全站重抓会耗尽额度 | 列表/详情双队列 + 每来源间隔与并发限制 + 近期项目定期复查、长期项目只留最后核查时间 |
| 翻页中断 | 当前页发现全部落库后才推进断点；进程中断后租约过期可重新领取，`epoch` 防止旧执行者覆盖新结果 |
| 某份详情失败 | 发现记录独立落库不丢失，也不阻塞其他来源 |
| 空列表 | 只有携带**样本站点声明的结束标志**才判定到尾，否则保留断点续抓 |
| 发布时间晚 ≠ 必然取代早公告 | 更正必须**明确引用对象 + 作用范围**；无引用/范围不明/相互矛盾一律转待核实 |
| 取消更正 | 被取消的更正内容完整保留（标记 `superseded`），取值以取消通知载明内容为准，**不回退最早值** |
| 不同标包截止时间不同 | 按 `项目+标包+字段` 分别保存；仅“适用于全部标包”的通知才能共同更新项目级字段 |
| 半份内容/解析失败 | 原件与错误都保留，缺失字段**不视为删除要求**，不产生采用结论 |
| 未确认内容 | 永远不替换当前采用结论；工作台逐字段确认或退回 |
| 导出 | 导出前重新核验所用公告是否被撤回/不可访问，清单保留所用修订与指纹 |

## 2. 目录结构

```
.
├── backend/
│   ├── cmd/server/         # 主服务：迁移、种子、采集 worker、Gin API、托管前端
│   ├── cmd/sampleserver/   # 多来源样本站点（单进程三站点 + 故障注入控制端点）
│   └── internal/
│       ├── db/migrations/  # SQL 迁移（内嵌进二进制，启动自动执行）
│       ├── sampledata/     # 样本数据集与 HTML 渲染（固定 data-sample-* 标记）
│       ├── fetcher/        # 按来源隔离的间隔/并发限流 + 有限重试
│       ├── parser/         # 列表/详情解析、指纹、半份内容识别
│       ├── worker/         # 列表、详情、复查三个调度循环与租约
│       ├── store/          # PostgreSQL 数据访问（租约、断点、关联、更正、复查）
│       ├── service/        # 关联/更正/采用/复查业务规则与人工工作台
│       └── api/            # Gin 路由、会话认证、处理器
├── frontend/               # Vue 3 工程（登录、来源队列、项目时间线、待核实、更正处理）
├── scripts/run_local.sh    # 本地一键启动（无需 Docker）
├── Dockerfile              # 多阶段构建，target: app / sample
└── docker-compose.yml      # db(PostgreSQL18) + sample + app
```

## 3. 本地启动

### 方式 A：Docker Compose（推荐，一键）

```bash
docker compose up --build
```

- 主平台（前端 + API）：http://localhost:8080
- 样本站点：http://localhost:9090 （`/healthz`、控制端点 `/control/*`）
- PostgreSQL：`localhost:5432`，库/用户/密码均为 `procure`

启动后 app 自动执行迁移、写入测试账号与三个来源，并为每个来源入队一次全量列表采集。

### 方式 B：本机运行时（本仓库默认环境已预装 Go/Node/PostgreSQL）

```bash
# 1. 构建前端（后端会托管 dist）
cd frontend && npm install --cache ./.npm-cache && npm run build && cd ..

# 2. 一键启动样本站点 + 后端（默认连本机 ccdev 库，自动迁移/种子/采集）
./scripts/run_local.sh
```

前端热更新开发：终端 1 跑 `./scripts/run_local.sh`，终端 2 跑 `cd frontend && npm run dev`，访问 http://localhost:5173 （`/api` 已代理到 8080）。

主要环境变量：`DATABASE_URL`、`SAMPLE_BASE_URL`、`HTTP_ADDR`、`LEASE_DURATION`、`POLL_INTERVAL`、`REVIEW_INTERVAL`、`REVIEW_RECENT_WINDOW`、`FAILPOINT_LIST_ABANDON`（故障注入，见第 6 节）。

## 5. 页面与操作路径

1. **来源与队列（admin）**：按来源查看「列表已发现 / 详情待取 / 待复查」计数、断点与作业 epoch；暂停仅停止新领取（执行中任务照常完成）；手动补抓与自动采集共用限流器，绕不开站点限额。
2. **项目时间线**：项目与标包分别计数；同一页并列展示**下载原件**（各正文版本、指纹、解析状态、原始 HTML）与**采用结论**；时间线汇总公告、更正、复查记录。
3. **待核实工作台**：两个页签——更正通知（含矛盾待核实）、关联候选（缺采购编号）。
4. **更正处理**：每个字段并列「原采用值 / 新提取值 / 原文位置 / 原文片段」，可逐字段**确认**（立即形成可追溯采用修订）或**退回补查**（当前值不变），也可整份退回。
5. **导出**：导出前复核撤标/不可访问/未处理更正，输出保留所用公告编号、版本 ID 与指纹。

## 6. 四个演示场景的复现步骤

> 下列命令基于方式 B 的本机服务；样本站点控制端点见 `backend/cmd/sampleserver/main.go`。

### 场景 1：翻页中断 → 租约过期重新领取（epoch 递增、断点续抓）

```bash
FAILPOINT_LIST_ABANDON=page-site:1 \
DATABASE_URL=postgres://ccdev:ccdev@127.0.0.1:5432/ccdev?sslmode=disable \
LEASE_DURATION=8s /tmp/pw-server   # 或在 run_local 基础上带该环境变量重启
```

- 列表作业在第 1 页保存后模拟进程中断，作业保持 `running`；
- 8 秒租约过期后被重新领取，`list_jobs.epoch` 由 1 变 2，从断点继续抓到结束标志；
- `A-001` 等已发现编号不重复入库（唯一约束 + 发现即落库）。
- 观察：来源页「列表作业」epoch、断点 `{"done":true,"page":3}`。

### 场景 2：重复发现 + 失效链接不等于撤标

- 样本站 A 第 1、2 页都含 `A-001`：`discovery_items` 仅一条（重复发现被去重）。
- `A-005` 详情始终 404：详情作业与发现记录标记 `inaccessible/不可访问`，但**没有任何项目因此改状态**；对比 `B-007` 明确撤标公告把 `PRJ-B-210` 置为 `withdrawn`。

### 场景 3：原址换文（同 URL 正文被替换）

```bash
curl -X POST "http://127.0.0.1:9090/control/revise-stage?stage=stage2"
```

- `C-001` URL 不变、正文指纹变化；复查抓取留存**第二个正文版本**，差异（截止时间 12-18 → 12-25）生成状态为待核实的差异记录；
- 在采购专员确认前，当前采用值仍是旧值 `2026-12-18 17:00`。
- 同时 `C-002` 由半份内容变为完整：旧截断版本（含解析错误）保留，新版本补齐 contact/budget，且未把缺失字段当删除。

### 场景 4：一份更正只影响部分标包 + 取消更正

- `COR-B-200-01` 仅适用 `PKG-02`：只生成该标包的字段变更，`PKG-01/PKG-03` 截止时间不变。
- `CC-B-200-01` 取消该更正：原更正标记 `superseded` 且内容保留；确认取消通知后，`PKG-02` 截止时间按取消通知载明的 `2026-12-10 17:00` 形成 `cancel_correction` 修订，而不是回退到更早的中间值。
- 尝试确认已 `superseded` 的 `COR-B-200-01` 会被接口拒绝。
- 预算更正 03 号（1350 万）与 04 号（1280 万）相互矛盾、`COR-B-200-05` 无明确引用对象：均自动置为“矛盾待核实”，等待人工判定。

### 附：拒绝访问有限次重试

样本站默认对 `B-001` 前两次请求返回 403（`/control/state` 可查请求计数）。fetcher 按来源配置 `max_retries=3` 退避重试，第三次成功；404/410 不重试，直接记不可访问。

## 7. 关键设计与数据模型

- **双队列**：`list_jobs`（整站串行，唯一索引保证同来源单一在跑作业）与 `detail_jobs`（按来源 `max_concurrency` 限流）分开排队，互不阻塞。
- **租约与防覆盖**：每次领取生成唯一令牌写入 `worker_id` 并设 `lease_until`；列表作业用 `epoch`、详情/复查用令牌回写校验。中断后旧执行者的回写因 epoch/令牌不匹配被拒绝，不能覆盖新结果。
- **结束标志**：空列表必须携带与来源 `end_marker` 一致的样本声明才到尾，否则保留断点。
- **版本与指纹**：`documents` 1:N `document_versions`，指纹为规范化正文的 SHA-256；同指纹不重复建版。
- **采用结论**：`adopted_revisions` 对 `项目+标包+字段` 维护唯一当前值，每次确认追加修订并作废旧值，完整保留来源文档/版本/更正链路。
- **复查**：近期项目（`REVIEW_RECENT_WINDOW` 内）按 `REVIEW_INTERVAL` 周期复查；超窗项目停止自动复查，页面仅展示 `last_checked_at` 与提示，不声称仍有效。

## 9. 已执行的验证结论（均为实际运行结果）

- 三来源列表均在携带结束标志的空页处正确到尾；页码/游标断点正确推进与持久化。
- 17 条发现去重后落库；16 份详情成功、`A-005` 记为不可访问且无项目被错误改状态；`PRJ-B-210` 仅因明确撤标公告变为 `withdrawn`。
- 分标包截止时间分别保存；缺编号的 `A-004` 生成关联候选，人工新建项目确认后才形成采用结论。
- 矛盾更正与无引用对象通知进入待核实；逐字段确认、退回、被取消更正拦截、取消更正保留新值均经接口验证。
- 原址换文产生第二正文版本与待核实差异，确认前采用值不变；半份内容原件/错误保留，修复后补齐字段。
- 故障注入下翻页中断后 epoch 递增、断点续抓、无重复发现；暂停来源期间新作业保持 `pending` 不被领取。
- 导出撤标项目带撤标警告，正常项目核验通过并输出版本与指纹。
